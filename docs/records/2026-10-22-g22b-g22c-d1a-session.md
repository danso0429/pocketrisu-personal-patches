## 4. G2.2b — BG `getCurrentLorebookEntries` parity

### 4.1 Goal and design (from the G2.2b plan)

RCM 1.0.21 calls `getCurrentLorebookEntries?.()` while preparing memory and continues with an empty list when the API is absent. In BG requests the API was absent, so memory preparation silently ran without lorebooks.

The BG per-request plugin host had to return the same entries in the same order as the foreground patched API:

1. the character's `globalLore`;
2. the selected chat's `localLore`;
3. the module lorebooks resolved natively by `getModuleLorebooks()` (`db.modules` order, id/namespace match, id de-duplication).

### 4.4 Decisions during G2.2b

**Cold-storage selected character (`character.coldstorage`) is not rejected by the new handler.** Owner decision, after a detailed explanation. Facts established from source:

- PocketRisu 1.10 clients never set `coldstorage`; only its type exists.
- The server restores or neutralises cold characters whenever it decodes the database:
  - at startup chat-store initialisation;
  - on `/api/read` and `/api/patch`;
  - on storage restore.
- Only a raw `/api/write` of `database.bin` caches an incoming database without that repair. Not reproduced.
- RCM calls `getCharacter` and `getDatabase(["characters"])` before `getCurrentLorebookEntries`. Both existing handlers hydrate and already reject cold characters. So for RCM the outcome is the same either way.
- The foreground patched API does not check `coldstorage` either.

**What RCM does when a context API fails.** Established from the pinned RCM 1.0.21 JS:

- The memory-preparation context builder (`ln`) is not guarded by its own try.
- A failure reaches the outer catch of RCM's `beforeRequest`, which logs `beforeRequest blocked` and rethrows as `MemoryInjectionBlockedError`.
- There is no retry, timer or empty-list substitute; the next chance is the user's next send.
- What happens next depends on the host:
  - **Foreground:** the request is blocked.
  - **BG before D1-a:** the failure was noticed and the request continued without memory.
  - **BG after D1-a:** the request fails.

## 6. D1-a — plan and review

### 6.1 Problem and decision

In BG operations the plugin host wrapped every hook so that a `beforeRequest` replacer failure recorded a notice, disabled the plugin and returned the unchanged messages: the request continued without the plugin's effect. Owner decision D1-a (2026-10-17) was native parity: the failure fails the request, the model is not called, the input is preserved, a notice is shown, and nothing re-runs automatically.

### 6.2 Facts established before planning (exploration, then checked by the orchestrator at the cited lines)

- The native replacer loop (`request.ts:252-256`) has no try. `sendChat` (`index.svelte.ts:1617`) and the direct lifecycle wrapper do not catch either. A host rejection therefore reaches the orchestrator's `fullThrew`, after the provider-effect latch.
- From there the orchestrator produces `terminal-error`, a `generation_failed` notice and the failed settlement of the attached server input. The exploration found no automatic re-run of this terminal state.
- Hooks are installed only for entries that did not fail at load (`bgPluginHost.cjs:671`). Load-time exclusions therefore keep the existing "proceed with notice" rule.
- An inventory of probe assertions found 14 existing expectations that depend on fail-open for an execution failure, and listed the unchanged identity, cancellation, provider, body, afterRequest and script cases.

### 6.3 Owner decisions taken while planning

1. A plugin already disabled by an execution failure earlier in the same operation, for example by an input-script failure, also fails the request at its `beforeRequest`.
2. A plugin disabled because the user changed the plugin set during the operation (edit, disable, reorder) proceeds without it. In the foreground, unloading a plugin removes its hook and the request continues.

### 6.4 Astra plan review (one round, five findings adopted)

1. Identity classification must look at `code` and `api` together. Ambiguous identity, an added plugin and cache instability use `plugin_api_unsupported` plus an `api` value. The cause is recorded once, at the first real disable.
2. Auxiliary requests do not share one outcome:
   - memory summarisation before the reply is caught by the memory code, `sendChat` returns false, and the result is `terminal-error`;
   - emotion and image-prompt requests after the reply produce `terminal-partial`.
3. Cancellation must be re-evaluated after asynchronous settlement. A worker or sandbox timeout of its own is an execution failure, not cancellation.
4. A caught API rejection continues only while the entry stays enabled. Notice counts mean the final failure notice; earlier warnings stay.
5. "No automatic re-run" needs restart, result claim/ACK and reconnect checks.

The plan also gained a chain-stop assertion, a caught/uncaught local CAS pair and five more unchanged identity cases. One boundary case was classified explicitly and not objected to by the owner: an argument CAS conflict after an external edit counts as an execution failure.

### 8.3 reloadKeys finding (owner decision: separate unit after D1-a)

The auxiliary fixed test still failed for a reason that also applies to real data:

- characters have no initial `reloadKeys`;
- after the reply the native code runs `reloadKeys += 1`, which yields `NaN`;
- the worker RPC refuses non-finite numbers, so any `getCharacter` in a post-reply request of the same operation fails.

The effect before and after this change:

- **Before D1-a:** that plugin was silently disabled.
- **After D1-a:** the post-reply auxiliary request ends as `terminal-partial` with `generation_failed`, and the answer is kept. The foreground passes `NaN` through.
- **This unit:** the fixture was given `reloadKeys: 0`. No test for the NaN behaviour was added, and value packing was left unchanged.

## 9. D3 — output sync after the reply (design analysis)

### 9.1 Facts (checked by the orchestrator at the cited lines)

- RCM's afterRequest schedules a 1500 ms timer whose callback re-reads the chat and sends `/v1/turn/prepare` with `deferExtraction:false` and a 5 s timeout. Without `addRisuChatListener` this fallback is selected.
- In BG the host closes before the canonical chat commit, and the preview lock is released after the close (`bgOrchestrator.cjs:1034-1038`).
- Hook invocation scopes are released when the hook returns (`bgPluginSession.cjs:28-52`). A timer-originated RPC is rejected with `plugin_invocation_expired`, and RCM's unload clears the timer.
- The host's network/model call budget of 128 is shared by the whole host (`bgPluginHost.cjs:212,612`), not per plugin.
- RCM creates a fresh `crypto.randomUUID()` generation id per model request, so its timer condition can pass in BG.

### 9.2 Astra review (one round, adopted)

- **Gaps:**
  - an overdue timer must wait for the commit without being lost;
  - a callback returning does not mean the sync finished, because DA's promise is not returned;
  - the commit-time status routes do not represent a sync window;
  - other plugins' workers would live longer.
- **Option D proposed:** a commit-gated one-shot timer continuation, with provenance recorded by the worker's timer wrapper, a separate child scope and an absolute expiry.
- **Recommendation:** D + A (hold the preview lock through commit and sync), switching to D + B (an operation-owned snapshot) if measured contention is unacceptable.
- **Persistence evidence must be staged:**
  1. the saved message reached the backend source store (request body ids/hashes, validated response, backend readback);
  2. the follow-up job was accepted;
  3. derived memory is usable by the next turn.

  A bare 2xx is not enough.
- **Eight measurements** are listed before the structure is chosen.

The plan is `docs/BG-G2-2-D3-OUTPUT-SYNC-PLAN.md` in the planning repository.
