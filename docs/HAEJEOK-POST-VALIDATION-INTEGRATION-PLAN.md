## 4. Keep admitted: HJ01, HJ03, HJ04

### 4.1 HJ01 — Small chat width

Keep:

- `Small` 600px outcome;
- native `Standard`, `Wide`, and `Full` values;
- one owner spanning message cards, creator notes, composers, and theme
  presets;
- unknown-value fallback to Standard; and
- PocketRisu Standard-theme scope.

Do not add:

- HJ `chatLimitSize`;
- a second Personal width;
- HJ's message-only width owner; or
- forced width rules for unrelated/custom themes.

Reason: the current adaptation retains the distinct HJ result while
preserving stronger native host consistency. Focused tests and physical L3
already passed.

### 4.2 HJ03 — Korean character matching

Keep:

- ordinary substring behavior;
- choseong, partial Hangul, jamo, and whitespace-insensitive matching;
- both keyboard-layout mistake directions;
- romanized English-name matching;
- creator/tag fields;
- final-syllable bounded expansion; and
- existing canonical/mobile-recent result order.

Do not add automatically:

- HJ MainMenu;
- relevance reordering;
- favorites/hidden state; or
- a second character-order owner.

Reason: the current matcher is a focused superset at the required input
boundary and its existing UI/L3 result is observed. Catalog presentation is a
separate value hypothesis.

### 4.3 HJ04 — persistence ordering

Keep:

- strict user-turn save before generation;
- script-clone merge into the identified live lazy chat;
- plugin tracker commit before runtime reload;
- browser-save exclusion inside the server orchestration bundle; and
- current lazy/BG/plugin-array authorities.

Do not add:

- HJ `MessageStore`, `SettingsStore`, or SQL domain stores;
- a second browser/server writer; or
- a top-level plugin-array replacement.

Reason: HJ has success-path ordering but its domain stores can clear pending
state and normally resolve after commit failure. The current adaptation stays
admitted because its own strict failure and L3 contracts are stronger, not
because it is SQL-equivalent.

when the stated trigger occurs and the user approves the design boundary.

### 5.2 HJ05 — low-spec slices

Trigger:

1. the same device/chat remains problematic after testing the existing
   initial/additional render controls; or
2. DOM, active message objects, image decode/network, character switching, or
   an owner-specific cache shows a reproducible bottleneck; or
3. the user explicitly requests a one-switch low-spec preset.

First-measure order:

1. mounted chat DOM;
2. active message-object memory;
3. image transfer/decode;
4. character/sidebar switch work; and
5. parser/blob cache growth.

Possible independent slices after measurement:

- a `manual | low-spec` derived render override that leaves saved manual
  values unchanged;
- a PocketRisu-native character-thumbnail path with exact URL identity,
  invalidation, and original fallback; or
- one owner-specific cache limit with exact blob lifecycle tests.

Explicitly excluded:

- HJ SQL `MessageStore`;
- active-chat 40-message compaction;
- generation/save/edit over an incomplete current chat; and
- one aggregate switch that silently acquires multiple authorities.

Stop the cycle if the selected slice has no observed user-path benefit or
moves responsiveness/availability cost to another session or owner.

### 5.3 HJ07 — Node token/lore/vector compute

Trigger:

- a specific client-only path shows a reproducible preprocessing bottleneck.
  Ordinary current BG sends are excluded from the benefit baseline because
  they already run server-side.

Stage order, one at a time:

1. token counting;
2. non-recursive lore matching;
3. recursive lore resolution; and
4. vector index/ranking.

Required comparison for each stage:

- identical browser-only and Node-assisted inputs/outputs;
- end-to-end client behavior, not a microbenchmark only;
- client responsiveness;
- Node event-loop delay and concurrent generation latency;
- warm/cold memory and index cost;
- request size;
- abort, restart, invalid regex, revision change, and fallback;
- unsupported tokenizer; and
- custom/local provider preservation.

No stage advances unless it improves the exact user path without moving the
stall or availability cost to other sessions.

## 6. Blocked format work: HJ06

The HJ ZIP64 writer is observed valid for one 4 GiB+1 entry and 65,536
entries. HJ06 remains blocked because:

- the HJ importer accepted a bad-CRC entry;
- HJ import still caps one entry at 50 MiB;
- current CharX import caps one entry at 50 MiB and selected payload at 1 GiB;
- current full backup is not ZIP;
- HTTP interruption/browser save/other extractors remain incomplete; and
- no actual current CharX export failure has established a user requirement.

Reopen only when all of these hold:

1. a valid current CharX export actually fails;
2. one export/import entry and aggregate size policy is approved;
3. both sides enforce CRC, path, duplicate, overlap, count, truncation, and
   cancellation policy;
4. writer→current importer and external extractor round trips pass;
5. interrupted HTTP/browser save is bounded and recoverable; and
6. physical iPhone Files save/open is observed.

The ZIP writer's existence or validity alone cannot unblock the feature.

## 7. Rejected frozen implementation: HJ08

Reject the frozen LogExporter implementation because observed final callers
have:

- active input attributes after the `notrim` sanitizer boundary;
- unvalidated restore schema and HTML/custom-style boundaries;
- numeric range identity that diverges after compacted-chat full hydration;
- incomplete edit, selected-theme, message-split, and MIME wiring;
- a UMD ffmpeg core load failure; and
- no caller for WebM conversion.

Do not import:

- HJ LogExporter components or renderer wholesale;
- HJ restore JSON;
- numeric-index ranges;
- HJ image splitting;
- frozen UMD/CDN media wiring; or
- WebM→WebP code.

A future exporter request is a new **current-owner project**, not a reopening
of the frozen HJ08 implementation. Its order is:

1. fix current native HTML metadata entity encoding;
2. define stable message identity for export;
3. add TXT/Markdown “this message only” and “from here” if explicitly
   requested;
4. preserve full `risuChat v2` JSON as full-chat only;
5. define a new type/version and new-chat semantics before any JSON excerpt;
6. close sanitizer and restore schema before visual HTML; and
7. treat any media engine as a separate offline/CSP/licensing/product
   decision.

Finding a current exporter defect does not admit HJ08.

## 10. One-feature admission protocol

A trigger does not authorize code immediately. Every future outcome starts a
fresh plan with the following gates.

### Gate 0 — exact baseline

- confirm current worktree/branch/remote/status;
- re-pin official PocketRisu and source revision;
- recompute exact target units, paths, and semantic owners;
- audit final modifier commits, not only origin commits; and
- confirm the user trigger is still present.

### Gate 1 — seven-axis owner report

Record source fact, final caller, state lifecycle, safety, test/runtime,
user value, and admission owner independently. Name current counterexamples
as aggressively as HJ counterexamples.

### Gate 2 — design approval

Agree on:

- user screen and trigger;
- existing owner;
- persisted state/schema and migration;
- default/off behavior;
- preserved settings, environment branches, custom endpoints, and local
  providers;
- failure, cancellation, retry, privacy, and deletion boundaries; and
- concrete physical L3.

### Gate 3 — isolated implementation

- one owner-local outcome per cycle;
- one feature commit;
- separate receipt/document commit;
- only necessary hidden adapters;
- no public combination selector; and
- no unrelated source or generated-artifact change.

### Gate 4 — focused qualification

- pure/helper/component tests;
- owner regressions;
- failure injection;
- cancellation and resource cleanup;
- security/privacy/adversarial inputs;
- exact-target apply/current/zero-change replan; and
- exact byte/mode revert.

### Gate 5 — complete graph

- complete patcher suite;
- focused current client/server tests;
- frontend/server/compat suites;
- Svelte diagnostics;
- production client and BG bundle;
- zero-change complete replan;
- clean-target exact revert/reapply; and
- source attribution and sensitive-information sweeps.

### Gate 6 — live candidate

- read active generation/import/restore state without mutation;
- wait without cancellation if work is active;
- process-first stop;
- apply the complete all-or-nothing transaction;
- build, production prune/load, and restart;
- compare served/local artifacts; and
- verify database, backup, operation, and error-log preservation.

### Gate 7 — feature-specific L3

Use the real user screen, button, gesture, visible state, and persistence
scenario. Multiple features may share one device session, but each result is
recorded independently. Existing HJ01/HJ03/HJ04 L3 is not repeated without a
regression signal.

### Gate 8 — documentation and release boundary

Update provenance, notices, comparison/audit/runtime receipts, README,
CHANGELOG, version/generated artifacts, and sweeps in one flow. A new HJ
feature remains experimental until its own gates pass. Stable tag/release is a
separate aggregate decision after the broader exact-1.10 catalog is verified.

1. Keep `.21`, its 38-pack graph, and HJ01/HJ03/HJ04 unchanged.
2. Start no additional HJ implementation now.

The evidence supports three admitted HJ outcomes and zero immediate additions;
everything else has a named trigger, blocker, rejection reason, or separate
product boundary.
