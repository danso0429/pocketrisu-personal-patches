# MARP BG 구현 완료 후 검증과 검수 기준

작성일: 2026-10-09 KST. 용도: 구현 완료 후 담당자에게 전달할 실행·검수 문서. 이 문서는 검증 결과나 통과 기록이 아니다.

## 1. 검증 목적

PocketRisu가 채팅 요청을 서버에서 인수한 뒤, 사용자가 화면을 전환하거나 홈 화면 앱을 닫아도 **MARP 분석 → 분석 결과 주입 → 본 답변 생성 → 후처리 → 원래 채팅 저장**을 이어서 수행하는지 확인한다. 앱 복귀가 실행이나 저장의 필수 조건이어서는 안 된다.

원본 MARP Lite를 공통 서버 플러그인 호스트에서 실행하는 방식이 기준이다. Lite를 Full로 교체하거나 MARP 전용 backend로 재작성하지 않는다. 설정 화면은 앱에 유지하고, 기존 모델·공급자·에이전트 선택·권한·재시도 동작을 보존한다. 플러그인별 프로세스는 한 작업의 입력·분석·본 생성·후처리 동안 유지하고 작업 종료 후 닫는다. 다음 작업에 이전 작업의 메모리 상태를 넘기지 않는다.

검수는 API 존재나 합성 테스트 통과만 확인하는 것이 아니다. 배포된 최종 호출 경로, 원본 실행 의미, 상태 수명, 저장·취소·실패 보존, 실제 기기에서의 사용자 결과를 확인한다. 확인되지 않은 경로는 통과로 처리하지 않는다.

## 2. 범위와 경계

- 주 대상은 **채팅 보내기에 따라 실행되는 MARP와 BG 전체 생성 과정**이다.
- MARP 설정 화면의 연결 검사·텍스트 분석 테스트는 브라우저 경로의 비교 자료다. 해당 버튼의 성공은 서버 실행이나 앱 종료 후 완주의 증거가 아니다. 테스트 버튼 자체의 서버 이관은 별도 기능 범위다.
- 기존 BG 모델 요청 보존과 prepared main 보존은 유지한다. MARP 전체 과정 검증을 기존 기능이 전혀 없었다는 주장으로 바꾸지 않는다.
- 보호 시작점은 서버가 작업을 실제 인수한 뒤다. 버튼 클릭·파란 진행 표시·로컬 전송 준비만으로 서버 인수를 주장하지 않는다.
- 서버 인수 전에 앱이 닫힌 요청까지 보존한다고 주장하지 않는다. 인수 유실·ACK 유실·재접속 시 중복 접수 여부는 별도로 검증한다.
- 앱 종료와 서버 재시작을 구분한다. 서버 재시작으로 실행 문맥을 잃은 작업은 실패·복구 상태와 알림으로 처리하며, 자동 유료 재실행을 하지 않는 기존 결정을 따른다.
- 공급자 HTTP 오류·네트워크 실패·quota·모델 거절은 여전히 발생할 수 있다. BG는 공급자 성공이나 취소 시 과금 철회를 보장하지 않는다.
- Archive Center, TTS, 감정 이미지, 이미지 생성은 이번 MARP 검수의 통과 범위에 포함하지 않는다.

참고 관찰: 원본 MARP Lite의 브라우저 텍스트 테스트는 세계관 19.53초 성공 뒤 플롯·등장인물이 각각 17.82초 후 실패한 사례가 있었고, 이후 화면을 유지한 실행에서는 모두 성공했다. 원인은 확정되지 않았다. 이 관찰은 앱 상태에 따른 실행 보존을 확인해야 할 동기이며 특정 timeout·동시성 제한·iOS suspension의 증거가 아니다. 임시 요청 가로채기 구현은 이번 검수의 선행 조건이 아니다.

## 3. 검수 시작 시 고정할 기준

담당자는 아래 정보를 먼저 기록하고 검수 중 변경되면 새 기준으로 영향 범위를 다시 확인한다.

1. 실제 worktree/branch, 비교 기준 commit, 구현 commit 또는 dirty diff, 생성 installer identity, 적용된 pack/version, 배포 시점의 관리 파일 일치 여부.
2. 실제 PocketRisu·Node 버전, 설치 MARP의 Lite/Full·버전·원본 bytes/hash, 활성 플러그인 순서, 서버 호스트의 실제 활성 상태. hash는 identity 기록이며 실행 허용 목록이 아니다.
3. 채팅의 실제 main/sub/aux binding, preset/module 조합, 에이전트 활성 상태, 개별 override, strict mode, PDF/text, streaming·retry·fallback 설정. 값 중 인증정보와 실제 사용자 콘텐츠는 공개 기록에서 제외한다.
4. 저장된 권한과 설정의 기준. UI 메모리 반영, pluginStorage/인자 저장, 서버에서 읽는 값이 서로 같은 시점의 설정인지 확인한다.
5. 검증 대상 bundle과 기기에 실제 로드된 bundle이 일치하는지 확인한다. 기존 기록의 버전·기기 상태를 현재 사실로 재사용하지 않는다.
6. 합성 환경과 실제 공급자 환경을 구분한다. 합성 credential/provider/storage로 자동 검증을 먼저 하고, 실제 공급자 호출은 승인된 조건·횟수 안에서 진행한다.

구현 코드·installer·배포 상태 중 어느 것을 검수했는지 명확히 한다. 라이브가 기존 host OFF 상태라면 그 사실을 적고 원본 MARP 서버 실행 통과를 주장하지 않는다.

## 5. 자동 검증 시나리오

가능한 항목은 담당자가 직접 실행한다. 각 결과에는 실제 사용한 source/installer/caller, 시험 조건, 기대 결과, 관찰 결과와 한계를 함께 남긴다.

| ID | 시나리오 | 필수 확인 |
| --- | --- | --- |
| A1 | 원본 MARP bootstrap·정상 분석 | 실제 호스트에서 hook 등록·호출을 확인한다. 세 에이전트 활성의 한 정상 분석은 세계관 후 플롯·등장인물이 실행되고 각 결과가 나온다. disabled/override 조건에서는 설정에 맞는 호출만 발생한다. |
| A2 | 분석 결과의 main 주입 | 합성 분석 응답을 구별 가능한 값으로 제공하고 최종 main 요청에서 각 결과·위치·형식을 확인한다. 주입 블록 중복 0, 분석 없이 main만 실행한 가짜 성공 0. main·분석·OAuth·transport attempt 수는 별도로 센다. |
| A3 | native retry와 fallback | native 기준과 분석 재호출·기존 주입 제거·main 재시도를 비교한다. 합법적인 native 재시도는 보존하고, 호스트나 앱 복귀 때문에 추가된 실행은 없어야 한다. |
| A4 | 느린 헤더·본문, 분석 timeout | 원본 deadline과 오류·strict mode 의미를 비교한다. 종료 후 callback·stream·handle을 정리하고 다음 정상 시도가 정상 동작한다. abort를 공급자 취소·환불 증거로 쓰지 않는다. |
| A5 | 분석 HTTP 오류·빈 결과·부분 성공 | HTTP 400/429/5xx, 연결 거절, HTTP 200 빈/잘못된 분석, 한 에이전트 실패를 나눠 시험한다. 원본 처리·설정과 동일한 main 진행/중단·주입을 확인한다. |
| A6 | 설정 저장 직후 보내기 | 개별 모델·에이전트 on/off·prompt·timeout 등 변경이 인자와 pluginStorage를 거쳐 실제 서버 실행에 반영되는지 확인한다. queued 작업의 설정 시점도 별도로 확인한다. |
| A7 | 외부 헤더 | 실제 최종 nativeFetch 경로에 활성 규칙이 적용되고 기존 사용자 헤더를 덮어쓰지 않는지 확인한다. 대화별 문맥과 브라우저 검사 경로의 fallback 문맥을 구분한다. session 오류 제거만으로 분석 성공을 판정하지 않는다. |
| A8 | 브라우저 종료 후 서버 완주 | 서버 인수를 확인한 뒤 브라우저 실행을 실제 중지한다. 분석 도중·main 도중 각각 시험하고, 브라우저 복귀 전에 normal-chat API로 원래 채팅의 완성된 저장 본문을 확인한다. 앱 없이 분석→main→후처리→저장이 이어져야 한다. |
| A9 | 복귀·cold reload·ACK 유실 | 새 브라우저 문맥에서도 정상 채팅의 결과를 채택한다. 앱 복귀가 저장을 대신 수행하거나 provider/분석/main을 다시 호출하지 않는다. 저장 중복·답변 유실·끝없는 busy·반복 경고를 확인한다. |
| A10 | 취소와 no-resurrection | 세계관·후속 분석·main 대기에서 whole-pipeline 취소를 시험한다. 늦은 완료·재접속·retry·N+1이 취소된 작업을 살리거나 결과를 잘못 저장하지 않는다. 새 작업은 정상 실행한다. |
| A11 | 서버 재시작·worker 종료 | input·분석·main 단계 문맥 상실을 나눠 시험한다. 자동 유료 replay 없이 기존 실패/복구 계약을 따른다. durable input·결과·알림을 보존하고 사용자에게 정상 재개로 오인시키지 않는다. |
| A12 | 대기 중 편집·삭제·N+1 | 앞쪽 메시지·설정 편집의 반영 시점과 수정 미반영 알림, anchor 저장, input/chat 삭제 시 conflict를 확인한다. N 저장 뒤 N+1 조립, reroll/이어쓰기 guard, 두 탭·오래된 사본 rebase를 확인한다. |
| A13 | 권한·혼합 플러그인·cold start | 권한 부재/만료·지원 안 되는 API·로드 실패·플러그인 순서·여러 활성 플러그인을 시험한다. 저장된 권한만 사용하고 호스트 실패를 알린다. 정상 플러그인과 기존 요청의 효과를 보존한다. |
| A14 | 자원·성능·조합·revert | 시작/응답 지연과 worker 정리·handle 수·resource cap을 측정한다. 전체 pack graph 적용·re-plan·exact revert, 저장소 build/type/lint/server 회귀를 수행한다. 과거 baseline 통과를 현재 qualification으로 승격하지 않는다. |

A8에서 실제 브라우저를 종료하지 못한 시험은 해당 한계를 적는다. 단순 network offline이나 페이지 표시 숨김은 브라우저 프로세스 종료의 대체 증거가 아니다. 직접 기기 시나리오가 남아 있으면 아래 항목으로 이어간다.

## 6. 실패 관찰과 진단 검수

호스트 실행 성공, HTTP 전송 성공, 플러그인 내부의 의미적 성공을 분리한다. MARP는 분석 오류를 내부에서 흡수하고 main이 실행될 수 있으며 HTTP 200도 사용할 분석이 있다는 뜻은 아니다.

1. 호스트가 확인한 load/crash·권한·지원 안 되는 API·자원 한도·provider 실패는 기존 실패/알림 계약을 확인한다.
2. transport summary가 있다면 호출 수·HTTP 상태·reject/abort·duration의 정확성, 유한한 보관·인증된 조회·민감정보 제외를 확인한다. aggregate summary만으로 최초 네트워크 원인이나 분석 품질을 판정하지 않는다.
3. 부분/빈 분석·원본의 private history/lastRun은 합성 응답과 최종 주입으로 직접 확인한다. 전송 요약이 원본 의미적 실패를 모두 복원한다고 주장하지 않는다.
4. 요청별 프로세스 종료 뒤 브라우저의 MARP 호출 기록에 서버 분석이 자동 표시되는지 확인하고, 표시되지 않으면 지원 한계로 명시한다. 설정 UI 보존과 진단 이력 보존은 서로 다른 계약이다.
5. 앱이 없는 동안 기록된 실패 알림이 복귀 후 보이는지, 중복 억제·ACK·TTL·기존 기기에서의 제한이 실제 관측 범위와 맞는지 확인한다.

실패 요청의 URL·credential·본문·실제 콘텐츠를 공개 문서나 로그에 추가하지 않는다. 검증에 필요한 합성 표식은 시험 자료에서만 사용하고 production 특수 분기로 넣지 않는다.

| ID | 화면과 손가락 조작 | 확인할 사용자 결과 |
| --- | --- | --- |
| D1 | MARP가 활성인 채팅에서 메시지 한 번 보내고 전면 유지 | 정상 답변이 원래 채팅에 나타난다. 담당자는 같은 작업의 분석·주입·저장 증거와 대응한다. 답변 표시만으로 세 분석 성공을 단정하지 않는다. |
| D2 | 새 메시지를 보내 서버 인수를 확인한 뒤, MARP 분석 중 다른 앱으로 전환 | 돌아오기 전에 서버 저장을 담당자가 확인한다. 복귀 시 답변이 나타나고 재전송·중복 답변·끝없는 생성 표시가 없다. |
| D3 | 별도 작업의 서버 인수 후 홈 화면 앱을 앱 전환기에서 종료 | 담당자가 앱 복귀 전 저장을 확인한다. 홈 화면 아이콘으로 다시 열어 같은 채팅에 결과가 있는지 확인한다. 자동 provider 재실행이 없어야 한다. |
| D4 | 분석이 끝나 본 답변을 생성 중인 작업에서 화면 잠금 후 복귀 | 본 생성·후처리·저장이 이어지고 streaming 설정에 맞게 완료 결과를 표시한다. |
| D5 | MARP 설정에서 개별 모델 또는 에이전트 on/off를 저장한 직후 채팅 보내기 | 서버가 새 설정으로 분석하고 설정 UI와 실제 실행이 어긋나지 않는다. |
| D6 | 처리 중 앞쪽 메시지를 편집하고, 다음 메시지를 대기열에 넣기 | 원래 입력 anchor에 답변이 저장되고 앞쪽 편집이 지워지지 않는다. 수정 미반영 알림과 다음 작업의 조립 시점이 계약에 맞는다. |
| D7 | 분석 또는 main 대기 중 취소한 뒤 앱을 닫았다 다시 열기 | 취소 작업이 부활하지 않는다. 이후 새 메시지는 정상 생성한다. |
| D8 | 합성 또는 승인된 실패 조건의 작업에서 앱 복귀 | 관찰 가능한 실패 알림과 정상 종료 상태가 표시된다. 재전송을 유도하는 가짜 성공이나 영구 busy가 없다. |

기기 기록에는 앱 형태·로드된 bundle·네트워크 종류·앱 전환/잠금/종료 구분·서버 인수 확인 방법을 적는다. iOS 강제 종료와 서버 종료를 혼동하지 않는다.

## 8. 검증 결과의 판정과 인계

실행한 각 항목은 `통과`, `실패`, `미검증`, `N/A`로 기록한다. N/A에는 설정이나 실제 경로에 따른 사유를 적는다. 통과에는 재현 조건과 직접 관측한 근거 위치를 붙인다. 원본 source 존재·hook 반환·HTTP 200·브라우저 답변 표시 중 하나만으로 전체 완료를 주장하지 않는다.

검수 보고서에는 다음을 포함한다.

- 비교 기준과 최종 구현·installer·배포 identity, 검수한 변경 경로와 최종 caller 순서도.
- A1~A14 및 D1~D8의 결과, 실행한 명령과 관찰값, 미실행 경로와 이유.
- 정상 분석·main 주입·서버 저장·복귀 채택을 같은 작업으로 연결한 증거. 사용자 콘텐츠 대신 합성 자료를 사용한다.
- native와 다른 동작, 실패 보존·취소·재시도·설정 수명의 결함, 영향 범위와 근거.
- 원본 private history, 서버 재시작, 자원 한도, 알림 등 남은 제품 한계와 별도 후속 과제.
- 해당 저장소의 L1~L4 결과, 실제 기기 gate 결과, 활성화·stable release 허용 여부. 자동검증만으로 기기 gate를 통과 처리하지 않는다.

독립 검수자는 보고서의 주장을 그대로 승인하지 않고 현재 source와 선택된 실험을 직접 대조한다. 발견 없음도 정상 결과다. 실제 실패나 미확인 사항을 성공으로 바꾸지 않고, 필요할 때 직접 관련 수정·재검증을 수행한다. 사용자 release gate와 회귀 처리 절차는 기존 정본을 따른다.
